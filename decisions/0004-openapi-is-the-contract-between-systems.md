# ADR-0004: OpenAPI is the contract between systems

- **Status:** Accepted
- **Date:** 2026-10-01
- **Deciders:** Platform lead

## Context

[ADR-0003](0003-systems-integrate-through-public-apis-never-a-shared-database.md) makes each
system's HTTP API the only way in. The telemetry pipeline depends on three facts about the
command center's API: the incident request shape, the zone lookup, and the resolve endpoint.
If any of them changes without notice, alerts stop becoming incidents — silently, from the
command center's point of view, because the failures appear in the _pipeline's_ outbox.

Inside a system the problem is already solved: the API and console share a TypeScript
`contracts` package, so the compiler catches a mismatch
([ADR-0002](0002-one-repository-per-system-monorepo-inside.md)). Across systems there is no
shared compiler.

Hand-written API documentation has a known failure mode: it is right on the day it is written.

## Options

1. **Share the TypeScript contracts package across systems** — compile-time safety, but it
   couples releases, and assumes every future consumer is TypeScript.
2. **Hand-written API documentation** — readable, drifts from the code within weeks.
3. **OpenAPI generated from the code, published with each system, with drift detected in
   review** — the spec cannot claim what the code does not do, and a change to it is visible
   in the diff of the pull request that caused it.

## Decision

Option 3.

- Every system serves its OpenAPI document at runtime (`/api/docs`), generated from the NestJS
  controllers and DTOs, not written by hand, and commits it to the repository as
  `docs/api/openapi.json`. The command center does this today; the telemetry pipeline serves
  its spec but does not commit it yet.
- The committed spec and the human-readable reference are regenerated by the
  [api-docs pipeline](https://github.com/truongtankhanh/claude-code-pipelines#pipelines), which
  reconciles rather than rewrites: each run reports endpoints as `new`, `changed` or `removed`,
  so a contract change shows up as a reviewable diff.
- **Breaking changes** to an endpoint another system calls — removing a field, tightening
  validation, changing a status code — need a new version or a deprecation period agreed with
  the consuming system, recorded in that system's changelog.
- The consumer keeps its own minimal client for the endpoints it uses and a test against a fake
  of the provider (the pipeline's end-to-end suite runs against a fake command center).

## Consequences

- A contract change is visible in review on the provider side, where it is cheapest to stop.
- Consumers are free to be written in anything.
- The consumer's fake can drift from the real provider. Contract tests run against the
  provider's published spec would close that gap; not done yet, and accepted for one consumer.
- Generating docs needs discipline in the code: DTO classes with decorators, explicit response
  types. That discipline is enforced by review, not by tooling.

## Revisit when

A second consumer appears for the same API, or a contract break reaches a site — then
consumer-driven contract tests become worth building.
